# Daily games and limited usage counting

Apply `community.sql` before `games.sql`. Deploy `games.mjs`, `games-data.mjs` and the shared `validation.mjs` alongside the community Edge Function. The router calls `handleGames(action,payload,ctx)` for `game.start`, `game.answer`, `game.cancel`, `leaderboard.list` and `analytics.record`. `ctx` supplies a service client as `db`, a JWT-verified optional `user`, `requireUser()`, `now()` in milliseconds and `rateLimit(scope,limit,windowSeconds)`.

`game.start` accepts only game and difficulty. Each verified account has one daily attempt per game/level; reopening resumes it. Completion, cancellation or expiry uses that day's attempt. Days reset at midnight in Bangladesh (UTC+06); a round expires after one hour. Knowledge, photo and distance challenges have five questions; puzzle levels have 6, 12 or 20 placements. Personality remains a practice activity without a competitive result. The versioned editorial facts deliberately remain independent of visitor-created place changes, so a day's challenge cannot change halfway through.

`game.answer` accepts `{sessionId,answer:{choice,round,requestId}}`. `requestId` is a UUID generated once per answer and reused on a network retry. The server owns answer keys, current question, scoring and timing. A service-only, row-locking SQL function compares state revisions and atomically records at most one completed result. An identical last request returns the existing outcome; stale rounds and closed sessions cannot add points. The client never supplies account IDs, calculated scores or elapsed time. These checks resist simple score editing and request replays; they do not prove a human played or eliminate bots. Public geographic facts and practice questions are not secrets.

Photo scores range from 0–5000, knowledge and distance from 0–5. A puzzle must finish all placements; each wrong selection adds five seconds to its server-measured duration. Time includes network time. Leaderboards separate games and levels, select each opted-in player's best result in the last seven days or all time, and order by score descending then duration ascending. Removing public profile consent removes the identity from rankings immediately. Emails and private Auth UUIDs are never returned by leaderboard or public-profile endpoints.

Online game sessions and results are operational records required for scoring and available to the Deshpath administrator. Optional analytics are separate: practice participation and export events are sent only with device consent, and signed-in requests also require account analytics consent. Events contain a random per-tab session ID and allowlisted game/export/format fields. Photos, text, map names, selected places and location are excluded. No events are queued while offline or after opting out. Guest counts estimate sessions rather than exact unique people. Export events distinguish preparation, a download request and a print request; they cannot confirm a successful disk save. Raw events should be retained only as long as needed; production scheduling/retention is an owner operation.

Frontend integration: load `ranked-games.css` and `ranked-games.js`; the module adds its own section after `#gamesRoot`. `DESH_RANKED.renderProfile(mount, me?)` renders online results separately from local practice. `DESH_ACTIVITY.record(event,metadata)` silently ignores unconsented/offline/invalid events. Explicit settings use `setConsent(bool)`; account refreshes use `syncConsent(bool)` so they cannot override a device's explicit opt-out.

Run `node tests/ranked-games.test.cjs` and the normal test suite. The new unit tests cover deterministic challenges, game levels, server-side answer/scoring/timing, request replay, expiry, ownership scoping, forged payload rejection, privacy envelopes and consent. They do not replace live verification of SQL transactions, concurrent requests, public consent changes or browser exports; those checks must run during deployment with isolated test data.
